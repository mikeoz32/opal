# Opal Microservices Implementation Plan

**Goal:** Add Crystal-native, transport-neutral RPC and event infrastructure to
Opal while reusing application lifecycle, DI scopes, execution policies, and
Data transactions.

**Architecture:** One application owns at most one logical service identity.
Message controllers and typed clients depend on explicit integration DTOs.
Transport adapters handle broker I/O and settlement only; Opal owns compilation,
DI, policies, scopes, deadlines, and lifecycle.

## Current status

Completed through the typed-client P1 slice:

- application-wide `LF::ShutdownContext` and retry-safe extension quiescence;
- quiesce-before-stop ordering with root DI preservation on drain failure;
- HTTP/WebSocket intake and drain moved into the shared quiesce phase;
- generic `LF::Execution` policy contracts and pipeline orchestration;
- existing `LF::HTTP` policy API retained as transport-specific subclasses;
- generic-ancestry-safe DI service discovery.
- validated service, RPC target, event, and configurable reply identities;
- a versioned protocol profile with Tori-compatible, fully configurable
  physical topology namespaces;
- strict bounded JSON request, response, error, and event envelopes;
- byte-for-byte golden vectors generated by the Tori Py v1 codec;
- transport-neutral publication, delivery, receipt, subscription, settlement,
  lifecycle status, and client/server contracts.
- message-native execution context, argument metadata, policy bases, and
  orchestration reusing `LF::Execution` without an HTTP adapter.
- executable typed handler invokers with per-delivery DI scope ownership,
  pre-scope wire/deadline/metadata validation, and combined cleanup errors;
- an initial bounded deterministic in-memory broker with RPC replies,
  competing consumers, event pool/broadcast routing, settlement, redelivery,
  quiescing, and reply-route generations.
- a reusable adapter conformance harness covering lifecycle, routing,
  backpressure, settlement, retries, replies, events, drain, and reconnect;
- an application `ServerRuntime` that owns handler dispatch, sanitized RPC
  replies, settlement classification, and quiesce-before-close integration.
- bounded fiber-safe RPC orchestration and an explicit typed service-client DSL
  with strict response validation and distinct failure categories.

Next: evaluate the current CloudAMQP Crystal client against the transport
contract before selecting the RabbitMQ adapter implementation.

## P0: Framework foundations

### 1. Two-phase application shutdown

- Add `LF::ShutdownContext` with one application-wide deadline.
- Add retry-safe `ApplicationExtension#quiesce` with a compatibility no-op.
- Quiesce all extensions before stopping any extension or closing root DI.
- Preserve the runtime when quiescence fails.
- Move HTTP intake/drain behavior from `stop` into `quiesce` without changing
  public HTTP shutdown behavior.

### 2. Transport-neutral execution policies

- Extract common guard, pipe, interceptor, filter, and chain orchestration into
  `LF::Execution`.
- Keep existing `LF::HTTP` annotations and behavior source-compatible.
- Add transport-specific HTTP and message contexts without fake adapters.
- Test ordering, short-circuiting, exception replacement, and scoped policy
  cleanup for both transports.

### 3. Microservices core contracts

- [x] Add validated service, RPC target, event, and reply-route identities.
- [x] Add bounded JSON request, response, error, and event envelopes.
- [x] Define publication receipts, encoded deliveries, settlement
  recommendations, transport status, server/client transport interfaces, and
  subscription modes.
- [x] Keep the entrypoint opt-in and free of RabbitMQ dependencies.
- [x] Make physical topology namespaces configurable with Tori-compatible
  defaults.
- [x] Lock cross-runtime JSON compatibility with Tori-generated golden vectors.

### 4. Handler compilation and message scopes

- [x] Add transport-specific message context and policy contracts on top of the
  shared execution pipeline.
- [x] Add RPC/event annotations and explicit message controller discovery.
- [x] Compile immutable handler plans before intake.
- [x] Validate duplicate routes and handler signatures at compile time.
- [x] Generate typed executable invokers for controller DTOs and policies.
- [x] Enter and close one `message` DI scope per delivery.
- [x] Reject malformed or expired messages before resolving scoped dependencies.
- [x] Preserve both handler and scope-cleanup failures.

### 5. Deterministic in-memory transport

- [x] Model bounded queues, acceptance, routing, competing consumers,
  correlation, settlement, redelivery, and connection generations.
- [x] Add transport conformance specs used by every future adapter.
- [x] State explicitly that the in-memory transport provides no process
  durability.

## P1: Typed RPC and RabbitMQ

### 6. Typed service clients

- [x] Generate typed clients from explicit Crystal contract declarations.
- [x] Enforce request/response types, finite deadlines, correlation IDs, and
  bounded pending requests.
- [x] Distinguish rejection, timeout, remote public error, transport failure,
  and outcome-unknown failure.
- [x] Never retry accepted requests automatically.

### 7. RabbitMQ AMQP 0-9-1 adapter

- Evaluate the current CloudAMQP Crystal client against the conformance suite.
- Implement deterministic queue/exchange/binding declarations.
- Use publisher confirms, mandatory routing, manual ACK/NACK, bounded prefetch,
  exclusive reply queues, retry queues, and dead-letter queues.
- Test RabbitMQ 4 startup, topology conflicts, broker restart, deleted reply
  routes, unroutable calls, shutdown drain, and redelivery.

## P1: Data reliability

### 8. Transactional outbox

- Add an explicit outbox entity/repository contract and relay lifecycle.
- Persist domain changes and outbox rows in one Opal Data transaction.
- Claim work safely across replicas with PostgreSQL locking.
- Publish stable event IDs and mark publication only after broker confirmation.

### 9. Inbox and idempotency

- Add transaction-local event-ID deduplication helpers.
- Make duplicate delivery a successful no-op after prior committed effects.
- Cover concurrent duplicate consumers and rollback behavior on PostgreSQL.

## P2: Events, operations, and examples

### 10. Event subscriptions

- Implement service-pool, singleton, ephemeral broadcast, and bounded reliable
  broadcast subscriptions.
- Add bounded retries and dead-letter inspection APIs.

### 11. Operations and security

- Add readiness and transport status integration.
- Emit stable structured invocation logs and metrics hooks.
- Validate header limits and explicit authentication context propagation.
- Document TLS and least-privilege broker configuration.

### 12. Reference application

- Build gateway, catalog, orders, and notifications as separate executables.
- Give each stateful service its own PostgreSQL database and migrations.
- Demonstrate typed RPC, local transactions, outbox relay, event deduplication,
  readiness, graceful shutdown, and Compose smoke tests.

## Release gates

- focused and full Crystal specs;
- formatter and documentation checks;
- transport conformance suite against in-memory and RabbitMQ transports;
- PostgreSQL concurrency tests for outbox and inbox;
- Compose smoke test across independent processes and databases;
- no RabbitMQ dependency loaded by the base `require "opal"` entrypoint.

## Cross-repository compatibility follow-up

Opal's default topology is compatible with Tori Py v1 today. Custom topology
names require a coordinated Tori change: its RPC exchange is configurable, but
its RPC queue, event exchange/queue, reply, retry, and dead-letter namespaces
are still hard-coded in the audited implementation. The shared golden JSON
vectors do not depend on those physical names.
